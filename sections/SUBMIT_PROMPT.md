## 0. AI 활용 원칙 — 사람과 AI의 역할 분담

- AI는 **완성 답안을 대신 쓰지 않음.** 개조식 뼈대·근거 리서치·코드 구현 보조만 맡고, **최종 판단·검증·전사는 사람**이 함.
- 모든 AI 출력은 **사람이 읽고 교정**함(환각 제거·우리 관점 주입). 근거 자료는 **출처를 대조**하고 불확실한 것은 "확인필요"로 표기함.
- 판단 규칙·설계 결정은 사람이 정하고, AI에는 "그 결정을 실증할 근거를 찾아라 / 개조식으로 정리하라 / 코드로 구현하라"를 지시함.

## 1. 깃허브 협업 운영 시스템 (기술적 구성)

3인이 같은 GitHub 리포에서 동시에 작업하되 충돌 없이, 방향은 하나로 모으기 위한 자체 운영 체계를 구축함.

### 1-1. 자동 동기화 데몬 (`sync.sh`)
- 각자 노트북에서 `./sync.sh &` 한 번 실행 → 이후 git 명령을 손으로 치지 않음.
- 매 12초: `내 변경 commit → git pull --rebase(남들 것 병합) → git push`.
- 식별자 = **git 계정 이름**(`user.name`)을 파일명 안전형으로 변환 → `radar/<계정>.md` 자동 생성.
- **겹침 경고**: 두 명 이상이 같은 파일을 '작업중'으로 잡으면 🟡, 같은 줄을 동시 수정하면 🟥 경고 + 조율 안내.
- **현재 작업 현황**: 3명이 각각 지금 무슨 파일을 잡고 있는지 상시 표시.

### 1-2. 겹침 방지 레이더 (`radar/<계정>.md`)
- 새 작업 전 자기 레이더의 "작업중:" 한 줄만 갱신 → 데몬이 이를 읽어 겹침을 사전 경고.
- 배타적 파일 소유가 아니라 "선점 표시 + 경고" 방식이라 유연하게 협업함.

### 1-3. 방향 통일 (`SPINE.md`)
- 팀이 합의한 핵심 전략·가정·차별점을 한 곳에 락(lock). **키잡이 1인만 수정.**
- 모든 섹션은 SPINE 기준으로 작성 → 세 사람 작업이 어긋나지 않음.

### 1-4. 병렬 에이전트 리서치 (워크플로우)
- 대규모 근거 수집은 **여러 AI 에이전트를 병렬로 fan-out** → 각자 다른 각도로 검색 → 결과를 **1개 에이전트가 중복 병합·카테고리 정리**하는 워크플로우로 수행함.
- 예: 사례 리서치는 11개 축(프록터링·성적산정·감정인식·취약계층·거버넌스·개인정보 등)을 동시 검색 후 종합. 데이터셋 리서치는 6개 신호군, 카메라 심화는 4개 각도로 병렬 수행.
- API 오류로 단발 에이전트가 끊길 때는 **자동 재시도·캐시 재개(resume)**로 복구함.

### 1-5. 에이전트 운영 지침 (코워크가 폴더를 열면 자동 적용되는 `CLAUDE.md` 요지)
```
너는 우리 팀의 작업 에이전트다. 출력은 완성 원고가 아니라
"그대로 옮겨 적을 개조식 뼈대 + 손으로 그릴 시각자료 설계도"다.
- 개조식, 짧게. 정확한 전문용어 환영, 군더더기 금지.
- 구조는 이 문제의 수행 과제에서 도출한다(고정 템플릿 아님).
- 가정은 "가정:" + 이유 반 줄. 불확실은 "확인필요:".
- 작업 전 radar 확인 → 겹치면 경고 → 내 레이더 갱신 → 편집. git은 데몬이 함.
- 모든 출력은 SPINE 기준으로.
```

## 2. 실제 사용한 프롬프트 — 기술 작업

### 2-1. 미션1 (판단 오류 분석) 프롬프트 (요지)
```
민원 10건에서 '판단의 근거가 된 문구'를 지목하고, 그 문구가 드러내는
기술적 결함을 완결된 문장으로 서술하라. 단순 나열 말고 여러 사례에서
반복되는 핵심 판단 오류로 분류하라. 각 진단을 실제 배치사례·선행연구로 검증하라.
분석 틀: Suresh & Guttag(2021) ML 피해 6원천(역사적·표현·측정·집계·평가·배치 편향).
```

### 2-2. 미션2 (하루쌤 2.0 판단체계 설계) 프롬프트 (요지)
```
하루쌤 2.0을 설계하라. 조건: 핵심 정보 3개+ 선택, 미선택 정보 직접사용 금지,
대부분 자동추천(교사 전원검토 불가), 판단보류·교사검토 20% 이하,
단일 신호로 확정판단 금지, 민감정보 수신자별 공개범위 결정, 새 정보 수집만으로 해결 금지.
- 최종 처리는 '규칙(결정 함수)'이 정하고 정보는 '신호'만 준다.
- 위험 신호 앞에선 점수 무관하게 사람에게 넘긴다.
- 모든 추천에 근거 한 줄을 남긴다.
각 설계 결정이 7개 조건 중 어디에 대응하는지 추적표로 매핑하라.
```

### 2-3. 코드 구현 프롬프트 (요지) — `sim/haruel2.py`
```
위 판단 규칙을 부작용 없는 순수 함수(같은 입력→같은 출력)로 구현하라.
ai_hypothesis(학생신호): 정서위기→교사검토(안전 오버라이드), 고성과+피로→감축,
협업→부정행위 자동판정 안 함, 성장추세→상향(라벨 고착 배제).
또래 대규모 데이터는 '참고 의견'으로만 두고 개인 신호·목소리가 우선(오프퀄 안전장치).
판단보류·교사검토가 20%를 넘으면 경계 사례부터 자동추천으로 되돌리되 정서위기는 제외.
```

### 2-4. 병렬 리서치 워크플로우 프롬프트 — 근거 수집 (실제 사용)
공통 배경(문제 개요 + 하루쌤 수집 신호 목록)을 각 에이전트에 주고, 아래처럼 축별로 분담시킴. 각 에이전트는 구조화 스키마(명칭·지역·연도·내용·타당성/위험·하루쌤 함의·출처)로 반환.
```
[각 에이전트 지시 예]
"이 축(예: 원격시험 감독 AI의 편향·피해 / 카메라 기반 참여도 인식 데이터셋 /
접속·과제제출을 feature로 쓰는 학습분석 데이터셋 …)에서 실존·문서화된
사례·선행연구·데이터셋을 4~8건 찾아라. 명칭·연도·출처(URL) 명시,
추측 금지, 불확실하면 '확인필요' 표시. 국내 자료 있으면 포함."

[종합 에이전트 지시]
"수집 목록을 중복 병합하고, 하루쌤 판단오류 패턴(또는 신호)별로 묶어라.
각 카테고리 끝에 '판단체계 시사점' 1~2줄. 표 쓰지 말고 개조식.
맨 끝에 출처 신뢰도 주의 + 국내:해외 비율."
```
- 산출물: `cases.md`(실제 사례 81건→9카테고리), `datasets.md`(핵심신호 데이터셋 47건→예측타당성), `camera.md`(카메라 신호 28건→채택여부 결론), `sim/evidence.md`(설계결정별 근거 라이브러리).

### 2-5. 품질 게이트 프롬프트 (점수 올리기 — 필요 시 사용)
```
- 발산:  이 문제의 서로 다른 접근 6개, 각 한 줄. 뻔한 것 말고 뒤집기·극단화·유추.
- 레드팀: 이 전략의 치명적 허점 3개 + 각 반박. 사정없이 공격.
- 차별화: 심사위원이 기억할 '한 방' 후보 3개(개념 이름/비유/반전).
- 자기채점: 창의성·논리성·실현가능성·전달력 1~5점 + 한 줄 근거. 3점 이하는 개선안까지.
```

## 3. AI 활용의 한계와 검증 절차

- 근거 리서치는 AI가 웹에서 모은 것이라 **일부 수치·URL·서지에 오류 가능성**이 있어, 각 파일에 "확인필요" 항목을 명시하고 인용 전 원출처를 사람이 대조함.
- 감정·집중도 판단처럼 **AI가 잘못 쓰면 학생에게 해가 되는 지점**은, 오히려 AI 리서치로 그 위험(편향·타당도 부족·규제)을 실증해 **설계에서 배제·제한하는 근거**로 활용함(카메라 신호 제외 결정).
- 최종 답안 문장·표·시각자료는 **사람이 직접 작성·전사**하며, AI 출력을 검증 없이 그대로 제출하지 않음.

---

> 요약: AI는 (1) 판단체계 설계·코드 구현의 보조, (2) 대규모 근거의 병렬 수집·정리, (3) 3인 협업의 자동 동기화·충돌 방지에 활용되었으며, 모든 결정과 검증의 주체는 사람이었다.
